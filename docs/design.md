# bettr 設計概要

## 目的

bettrは、AIエージェントがローカルでIssueを高速に読み書きし、人間が介入すべき箇所を横断的に監督するためのCLIです。GitHubリポジトリを作るほどではない作業にもIssue管理を持ち込み、Human in the loopからHuman on the loopへ近づけることを目的とします。

名前はDaft Punkの「Harder, Better, Faster, Stronger」に由来します。マルチプレクサの[[herdr]]をHarderに見立て、その次のBetterからeを抜いてbettrとしています。

bettrは状態管理と原子的な仕事の取得を担います。[[wayfinder]]はIssueを監視してエージェントの実行を調整し、herdrはエージェントを実際に動かします。bettr自身はエージェントを起動しません。人間は`bettr status`を通じて、判断待ちや停止した作業を監督します。

## 実行方式

bettrは[[Rust]]製の単一バイナリとし、macOSとLinuxを正式に対応します。データはユーザー単位の[[SQLite]]データベースへ保存します。HTTPや常駐デーモンは介さず、各CLIプロセスがデータベースへ直接接続します。同一マシン上の複数プロセスを正式に支えますが、ネットワーク越しの共有や外部データベースは初期スコープに含めません。

SQLiteはWALモード、短いトランザクション、busy timeout、自動再試行を用います。ロックを取得できない場合は明示的に失敗します。同一Issueに対する更新競合はリビジョン番号による楽観的ロックで検出します。既定のデータベースに加えて任意のSQLiteファイルを指定できますが、未知のパスに空のデータベースを暗黙作成せず、初期化には`bettr init`を要求します。

通常のローカル利用で別用途のSQLiteを誤指定しても変更しないよう、初期化済みデータベースを必要とするコマンドは、選択したpathが通常ファイル（symlinkの場合はその参照先）であることをSQLiteで開く前に確認します。
通常ファイルであればheaderを副作用なく読み、bettr固有のapplication IDとschema versionを検査します。
通過後はread-write接続を開き、その同じ接続上でidentityを再確認してからWALなどの接続設定を有効にします。
拒否時は既存bytesを変更せず、header preflightによって`-wal`、`-shm`、`-journal`を新規作成しません。

`bettr init`と`bettr context`はこの終了契約の対象外です。
既存pathに対する`init`はexit 2の`database_already_initialized`を返します。
別用途のSQLiteを指定した`context`はデータベースを作成または変更せず、解決したpathを返してexit 0で終了します。

このMVPの保証は非敵対的な誤指定を対象とし、完全なファイルシステム安全性は主張しません。identity確認とopenの間に敵対的な別プロセスが選択pathを意図的に置換するTOCTOUは保証外です。

プロジェクトは不変UUIDと人間向け名称を持ちます。Issueは内部UUIDとプロジェクト単位の連番を持ちます。CLIの設定はコマンド引数、環境変数、ディレクトリ設定、ユーザー設定、既定値の順で解決し、`bettr context --json`で解決結果と設定元を確認できるようにします。

## Issueモデル

Issueの状態は`todo`、`in_progress`、`blocked`、`done`、`cancelled`の5種類です。通常の状態遷移を制限し、例外的な強制遷移には理由を要求します。`blocked`には理由と`human`、`dependency`、`external`のいずれかの待機種別が必要です。`done`には完了サマリーと検証結果が必要であり、`cancelled`には中止理由が必要です。`failed`という状態や主観的な進捗率は設けません。

Issueには単独の担当、`critical`、`high`、`medium`、`low`の優先度、`blocks`による依存関係、一階層の親子関係、ファイル・URL・Gitコミットなどの参照を持たせます。本文とコメントはUTF-8のMarkdownとして保存します。投稿済みコメントは通常操作では編集または削除せず、訂正は新しいコメントとして追加します。

## 複数エージェントの協調

`bettr issue claim`は、Issueの選択、担当設定、`in_progress`への変更を単一トランザクションで行います。自動選択では、未完了の依存先がなく、人間の判断待ちではない`todo`を対象とし、優先度と作成日時によって順序を決めます。

claimはエージェント名とセッションIDの組に対するleaseです。各書き込み操作でleaseを自動延長し、長時間処理では明示的なheartbeatを使います。期限切れでも状態を自動変更せず、staleな`in_progress`として表示します。別セッションが取得する場合は、理由付きの`takeover`を要求します。

すべての書き込みは任意の冪等性キーを受け付けます。専用スキルとwayfinderは書き込み時に必ずキーを設定します。複数Issueの更新には、全件成功または全件ロールバックとなるJSONバッチ操作を提供します。

## 人間による判断

登録済みactorという独立した管理対象は設けません。どのエージェントとセッションがコマンドを実行したかを表す実行コンテキスト、Issueを進める責任の所在を表す担当、人間が与えた意味のある判断イベントを分離します。

判断待ちは単純なフラグではなく、個別IDを持つ`decision_request`として扱います。一つのIssueに複数の要求を持つことができ、問い、背景、要求元のエージェントとセッションを記録します。人間の判断は専用操作によって対象の要求を解決し、判断内容、判断者、状態変更を単一トランザクションで記録します。未解決の判断要求が一件以上あることを`attention_required`として派生表示します。

専用スキルは`BETTR_AGENT`と`BETTR_SESSION_ID`を設定します。エージェント名を親プロセスから推測する方法は補助にとどめます。呼び出し元のセッションIDを取得できない場合は、スキルが作業単位の`bettr_session_id`を生成し、その由来も記録します。人間によるCLIの直接操作は主要導線ではありませんが、実行主体の種別として`human`も扱います。

## CLIと監督ビュー

CLIは非対話式とし、引数、標準入力、環境変数だけで完結させます。端末では簡潔な表を返し、機械向けにはバージョン付きの`--json`と`--jsonl`を提供します。標準出力には結果だけを出し、警告や診断は標準エラーへ出します。入力不正、対象なし、競合、データベースの一時ロック、内部エラーは終了コードで区別します。

人間向けの主要導線は`bettr status`です。全プロジェクトを横断し、未回答の判断要求、staleな進行中Issue、blocked Issue、最近完了または中止されたIssue、現在稼働中のIssueの順で表示します。`issue list`は検索、`status`は監督という役割に分けます。

wayfinderは単調増加するイベント番号をカーソルとして、前回以降の変更だけを取得します。イベントは種別、対象ID、変更フィールド、変更後リビジョンを返し、必要に応じて変更後のIssue全体を含めます。各読み取りは一貫したSQLiteスナップショットを使います。初期版ではwatchや常駐通知を設けず、wayfinderが適切な間隔で差分を取得します。能力検出には`bettr capabilities --json`を提供します。

## 監査

監査はSQLite内の追記専用イベントを正本とし、外部向けに追記専用のJSON Linesログを持つ二層構造とします。成功と失敗、読み取りと書き込みを含むすべてのCLI呼び出しを記録します。ただし、生のコマンドライン、Issue本文、コメント本文、秘密値は監査ログへ保存せず、解析済みの操作名、対象ID、変更フィールド、実行コンテキスト、結果を記録します。

JSON Linesは一行一イベントとし、各行にスキーマバージョンと直前イベントのハッシュを含めます。複数プロセスの追記はSQLiteを介して直列化し、ファイルへの未反映イベントは次回実行時に復旧します。自動ローテーションはせず、明示的なarchive操作でハッシュチェーンを引き継ぎます。`bettr audit verify`で改変や欠落を検査し、必要な場合はSQLiteから再構築できます。

秘密情報を誤って保存した場合は、監査履歴を含めて内容を消去する管理操作を用意します。消去後も、誰がいつどの対象に消去操作を行ったかは残しますが、内容、生のコマンドライン、元の内容のハッシュは残しません。既存バックアップからは自動的に消去できないことを明記します。

## 実装段階

Phase 1では、プロジェクト、Issue、コメント、5状態、履歴、JSON出力、SQLiteの並行アクセスを実装します。後から復元できないため、SQLite内の監査イベント、実行コンテキスト、担当情報もこの段階から保存します。

Phase 2では、claim、lease、判断要求、依存関係、親子関係、イベントカーソル、冪等性を追加します。Phase 3では、監査JSON Lines、バックアップ、復元、機密情報の消去、`bettr doctor`を追加します。専用スキルは各Phaseと同時に提供し、その時点で実装済みのコマンドだけを利用します。

## 配布と将来

ライセンスはMITとし、[[GitHub]] Releasesからインストール可能にします。開発初期は`cargo install --path`でも利用できるようにします。最初の専用スキルはCodexとClaude Codeを正式対象とし、wayfinderは安定したJSON契約を直接利用します。

ネットワーク共有とSQLite以外のデータベースは初期スコープに含めません。`bettr web`はローカルloopback専用の読み取り監督ビューとして提供し、CLIとスキルを実作業で使う導線を補助します。Web UIはOverview、プロジェクト横断一覧、Issue詳細、保留型の更新インジケーターに限定し、変更操作はCLIに委譲します。人間が`bettr status`またはWeb UIから介入点を判断できること、エージェントが重複取得せずに引き継げること、判断要求のモデルが実運用に耐えること、JSON契約が安定していることを引き続き検証します。

性能目標は、一般的なローカルSSDで起動時間を含む単純な読み書きのp95を50ミリ秒未満、10万Issueに対する絞り込み一覧のp95を200ミリ秒未満とします。実装後のベンチマークで妥当性を検証します。
